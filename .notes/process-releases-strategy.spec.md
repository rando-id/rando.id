# Releases strategy — what ships when, recorded how

## Decision (proposed)

**Tier 1, start here:** `.github/release.yml` for PR grouping +
`.github/workflows/release.yml` (workflow_dispatch) that bumps
every `package.json` + `app.json` in the workspace to a single
`vYYYY.MM.DD` string, commits the bump, tags, and runs
`gh release create --generate-notes --target main`. One repo,
one version, every surface. Zero third-party actions, zero
versioning tooling beyond a ~30-line Node script. One-button
release from the Actions tab when we want to cut a ship log.

**Tier 2, if cadence pushes us:** switch the workflow trigger to
`push: branches: [main]` so every successful main commit auto-tags.
Same release-creation logic, just no manual button.

**Skip:** release-please, changesets, semantic-release. All
optimize for npm-publishing flows we explicitly decided against
(see [[tech-pnpm-turbo]] and the broader monorepo discussion —
`@rando/*` packages stay internal). Version-bumping ceremony has
no consumer here.

## Why GitHub-native

- **One platform, zero auxiliary tools.** Release notes are generated by GitHub itself, configured via a single YAML file, triggered via the CI infrastructure we already maintain.
- **No versioning _tool_ dance.** A ~30-line Node script bumps every `package.json` + `app.json` in lockstep. We're not publishing, so we don't need tools that manage SemVer ranges, peer-dep matrices, or per-package independent versioning. The version is one string, written everywhere by our own code.
- **Conventional-commit-friendly without conventional-commit lock-in.** `.github/release.yml`'s `categories:` config groups PRs by label (`enhancement`, `bug`, `chore`, `dependencies`, `breaking-change`). We can keep our `feat(scope):` / `fix(scope):` commit style and label PRs to match; if the labeling convention drifts, the worst case is "ungrouped" instead of "tool blows up."
- **`gh release create --generate-notes`** is the same command from a workflow OR a developer's terminal. Local/CI symmetry — fits the [[project_rando_cli]] pattern of `rando releases cut` wrapping the same logic later if useful.

## Version flow — single number, every surface

We use a **single, repo-wide version**. No per-package versioning,
no independent SemVer per workspace. The same string lands in every
place it's surfaced:

| Surface              | What gets stamped                                                          | How                                                                                                                                       |
| -------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Git tag              | `v2026.06.22`                                                              | release workflow                                                                                                                          |
| GitHub Release       | `v2026.06.22`                                                              | `gh release create`                                                                                                                       |
| Every `package.json` | `"version": "2026.06.22"` in `apps/*` + `packages/*` + root                | `scripts/bump-version.mjs` walks the pnpm workspace + writes                                                                              |
| OpenAPI spec         | `info.version: "2026.06.22"`                                               | contract reads `packages/api-client/package.json` at build time (see [[tech-api-rest-openapi]])                                           |
| API runtime          | `X-Rando-Version: 2026.06.22` response header                              | `apps/api` middleware reads its own `package.json` at boot                                                                                |
| Expo native          | `app.json` `version` + monotonic `ios.buildNumber` / `android.versionCode` | `bump-version.mjs` updates `app.json`. `runtimeVersion` stays manually controlled — only bump on native code changes (see [[tech-expo]]). |

Why locked-step:

- **No "which version of `@rando/api-client` works against which version of `apps/api`" question.** They're always the same build, identified by the same string.
- **Debugging matches the release index.** A user reports `v2026.06.22` and we can `git checkout v2026.06.22`, browse the release notes, and see exactly what shipped.
- **Vercel deploy URLs become greppable.** The bump commit + tag are visible in Vercel's deploy list, so we can correlate prod incidents to releases without leaving the Releases tab.

## Options considered

- **GitHub-native (`.github/release.yml` + `gh release create --generate-notes`)** — recommended above. Pure GitHub primitives. Cost: requires PR labels to get the nicest grouping (mitigated by a labeler action or a one-line `release.yml` `exclude:` fallback).
- **Release Drafter** (GitHub Action) — maintains a _draft_ release that auto-updates as PRs merge; you click "Publish" when ready. Very lightweight, very GitHub-flavored. Lost on: nearly identical to `--generate-notes` on demand, except it carries persistent draft state. For our cadence (deliberate ship log, not continuous), on-demand wins.
- **release-please** (Google) — opens a release PR with auto-incremented version + `CHANGELOG.md` + tag-on-merge. Excellent fit for conventional-commit codebases. Lost on: opinionated about `package.json` version fields (dead weight for a non-publishing repo); monorepo config (`release-please-config.json` per package) gets dense; we'd run an action pipeline whose primary output (versioned tags, CHANGELOG.md) we don't actually consume. Best-case it gives us nicely-versioned tags + a changelog file; GitHub-native gives ~80% of that value for zero config.
- **Changesets** — contributors add markdown files describing each change; CI consumes them to bump versions + publish. Wrong shape for a non-publishing monorepo. Friction (a changeset file per PR) for value we don't extract. Also: changesets defaults to _independent_ per-package versioning — exactly the opposite of the lockstep flow we want.
- **semantic-release** — older auto-versioning + publishing tool. Heavier than release-please, more publishing-oriented. Same fit problem, more baggage.
- **Tag every push to main** — purest possible audit trail. Lost on: noisy (multiple commits/day during active work), and Vercel already maps git SHAs → deployments, so the audit trail exists in [[tech-vercel]]; pure tagging adds no information. Worth revisiting as Tier 2 only if we want a release per deploy AND we're cool with the tag noise.
- **Pure manual `gh release create` when you feel like it** — works for a solo dev. Lost on: easy to forget; the "what shipped when" goal is undermined if releases happen ad hoc with no workflow scaffolding.

## What we accept

- **Versions aren't SemVer.** Date-based (`v2026.06.17`) or numbered (`r42`) tags are fine — we're not publishing, so the version field is documentation, not API contract.
- **Manual triggering** means it takes discipline to actually cut a release. Mitigated by `workflow_dispatch` so it's one button click; further mitigated by a possible follow-up `pnpm rando releases cut` subcommand.
- **Multi-app deploy reality.** Web/admin/api deploy via Vercel; native via EAS (see [[tech-vercel]], [[tech-expo]]). A GitHub Release is repo-wide; if web deploys 3x and api deploys 0 times in a window, the release covers both. Granular per-app deploy history lives in Vercel + EAS dashboards. The GitHub Release is the human index, not the source of truth.
- **PR labeling is the prerequisite for good grouping.** Without labels, all PRs land under "Other Changes" in the auto-notes. Solve with either: (a) a GitHub `actions/labeler` workflow that adds labels by changed paths or PR-title prefix, or (b) a one-time team convention. Either way it's low cost.
- **Every release commits a `chore(release): vYYYY.MM.DD` bump to main.** Tiny — just version fields. Filtered out of the _next_ release's auto-notes via `.github/release.yml` `exclude.authors: [github-actions]`. Vercel will redeploy from the bump commit; effectively a no-op deploy but it stamps the new version header at runtime.

## Concretely, what we'd build

1. **`.github/release.yml`** — categories config + exclude `chore(release):` bump commits:
   ```yaml
   changelog:
     exclude:
       authors: [github-actions]
       labels: [release-bump]
     categories:
       - title: Breaking Changes
         labels: [breaking-change]
       - title: New Features
         labels: [enhancement]
       - title: Bug Fixes
         labels: [bug]
       - title: Dependencies
         labels: [dependencies]
       - title: Internal & Tooling
         labels: [chore, ci, docs]
       - title: Other Changes
         labels: ['*']
   ```
2. **`scripts/bump-version.mjs`** — tiny Node script (no deps; reads `pnpm-workspace.yaml` via `fs`). Walks every `apps/*/package.json`, `packages/*/package.json`, root `package.json`, and `apps/native/app.json`. Writes the same version string to each. Increments `ios.buildNumber` and `android.versionCode` monotonically (read prior tag from `git describe`, add 1). Idempotent — re-running with the same version is a no-op.
3. **`.github/workflows/release.yml`** — `workflow_dispatch` trigger with optional `version` input (default: today's date as `YYYY.MM.DD`). Steps: checkout → `node scripts/bump-version.mjs $VERSION` → `git commit -m "chore(release): v$VERSION"` → `git tag v$VERSION` → `git push --follow-tags` → `gh release create v$VERSION --generate-notes --target main`. Permissions: `contents: write`.
4. **`actions/labeler@v5` workflow** (optional, tier-1.5) — auto-labels PRs by file paths (`apps/web/**` → `scope:web`, `packages/api-client/**` → `scope:api`, etc.). Lets us extend the `release.yml` categories with per-app sub-groupings if we care.
5. **Follow-up issue** filed via `pnpm rando issues create` once we land on a final shape — referencing this file in the body per the [[CLAUDE.md]] workflow note.

## Sample cadence — a week in the life

Assume Monday weekly releases, aligned with our [[dependabot-triage]]
cadence. Last release was `v2026.06.15`.

```
Mon 06-15  09:00  Release v2026.06.15 cut → bump commit lands on main → Vercel
                  redeploys with the new X-Rando-Version header. Dependabot
                  opens weekly PRs.

Mon 06-15  morn   Merge #114 actions group, #136 react-dom patch.
                  Push to main → Vercel auto-deploys (commits still under v2026.06.15).

Tue 06-16         Merge #162 feat(api): rate limit /v1/auth/*. (Closes #88)

Wed 06-17         Merge #163 chore(repo): direnv bootstrap.
                  Merge #164 fix(ui): tamagui shorthand regression on web.

Thu 06-18         Merge #165 feat(maps): cache nominatim responses.

Fri 06-19         Quiet — only a docs PR (#166).

Mon 06-22  09:00  Cut release v2026.06.22 (workflow_dispatch from Actions tab).
                  Workflow runs:
                    1. bump-version.mjs 2026.06.22
                       → every package.json + app.json updated
                       → ios.buildNumber + android.versionCode += 1
                    2. git commit -m "chore(release): v2026.06.22"
                    3. git tag v2026.06.22 && git push --follow-tags
                    4. gh release create v2026.06.22 --generate-notes --target main
                  Auto-generated release notes group PRs #114/#136/#162/#163/#164/#165/#166
                  under "New Features", "Bug Fixes", "Dependencies", "Internal & Tooling".
                  The bump commit triggers a final Vercel deploy carrying
                  X-Rando-Version: 2026.06.22 at runtime — closing the loop.
```

Things to note:

- **Vercel still deploys continuously.** The release is a _snapshot label_, not a deploy gate. Production already had #114–#166 running before we cut the release; the release just names that state.
- **Patch releases work the same way.** Hot-fix needed Thursday? Land the fix, cut `v2026.06.18` mid-week. No special "patch" vs "minor" distinction since we're date-based and non-SemVer.
- **Two releases on the same day** are fine — append a counter: `v2026.06.18`, `v2026.06.18.1`, `v2026.06.18.2`. Rare in practice; budget for it.
- **The `chore(release):` commit is in git history but excluded from auto-notes** via `release.yml`'s `exclude.authors: [github-actions]` filter. Honest history, clean ship log.
- **Expo OTA vs native binary.** `bump-version.mjs` bumps `app.json` `version` + build numbers every release — but `runtimeVersion` stays put unless native code actually changed. JS-only releases ship via EAS Update without a new App Store submission; native releases bump `runtimeVersion` manually (one extra step, infrequent).

## What would make us reconsider

- We start actually publishing something to npm (a public CLI binary, a public component library). Then release-please's version-bumping logic earns its keep — and per-package independent versioning may become necessary if consumers depend on individual packages.
- `CHANGELOG.md`-in-the-repo becomes a contractual expectation (OSS contributors expecting it, security advisories referencing it). release-please writes one; GitHub-native release notes only live on the Releases tab.
- Release cadence becomes high enough (multiple per day) that manual triggering loses to fully-automated tagging. Switch to push-to-main Tier 2.
- GitHub deprecates or weakens `--generate-notes` (unlikely; it's a load-bearing primitive across their docs).
